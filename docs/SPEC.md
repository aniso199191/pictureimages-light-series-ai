# Series specification

## Product shape

`PictureImages Light Series AI` is a family of open-weight models intended to run
on consumer hardware. The repository publishes code, data recipes and weights;
it does not host inference.

| Field | Series target | Debug build (measured) |
|---|---|---|
| Parameters | 8–9 B total, MoE with sparse activation | reported in `RESULTS.md` |
| Context | 1M–1.5M tokens on a machine with enough RAM/VRAM | 512 trained, RoPE scaling supported |
| Modalities | text, image understanding, image generation, video generation, code, files, agent tools | text backbone only |
| Quantization | FP16 / BF16 / INT8 | FP16 / BF16 |
| Runtime | PyTorch reference; PimeraX export planned | PyTorch reference |

"FP12" as a storage format does not exist in current toolchains. 12-bit packing
is possible in principle but is not supported by PyTorch, llama.cpp or MLX, so the
series ships FP16/BF16 and INT8 instead of promising a format that cannot load.

## Groups

| Group | Data source | Purpose |
|---|---|---|
| `distill` | Q/A pairs generated by a larger teacher model through an OpenAI-compatible API, filtered for refusals, boilerplate and length | teaches answer style and factual coverage |
| `daily` | everyday conversation logs written for this project | teaches conversational tone |

Both groups are stored as JSONL with provenance fields. Teacher model names and
prompt versions are kept per record so the recipe can be audited.

## Long context

The 1M–1.5M token target is a design target for the 8–9 B series. Attention cost
and KV-cache size grow linearly with context; a 9 B model at 1M tokens needs tens
of gigabytes of cache even with grouped-query attention. The debug build supports
RoPE scaling (`rope_scale` in `ModelConfig`) so longer inputs do not crash, but
quality beyond the trained window is not claimed.

## Evaluation protocol

1. Validation loss on held-out documents (document-level split, no overlap).
2. Sample generations on a fixed prompt set, published verbatim, including bad ones.
3. No benchmark claims without running the benchmark on this checkpoint.
